Recover a fast interpreter before replacing it

The first solution is a staged interpreter cleanup that preserves FPAS behavior and the verified register bytecode. It targets costs already present at instruction, call, intrinsic, and global-access frequency. Every stage has its own rollback point.

Recommendation: begin with execution-policy separation. It is the smallest change that can explain the broad current regression and it creates a clean seam for later optimization. Do not start with computed goto, a garbage collector, or Cranelift.

Design target

Small interface

run_until_event(), resume(), and state inspection only through an explicit debug adapter.

Deep implementation

Instruction fetch, frame transitions, safepoints, task yielding, diagnostics, counters, and debug hooks stay behind the execution seam.

Two real adapters

A normal fast executor and a debugger executor justify the seam. Normal execution must not branch on debug state for every instruction.

Proposed module shape

crates/fpas-vm/src/vm/execution/
  mod.rs                 — narrow run/resume interface and shared outcomes
  fast.rs                — normal execution loop; no debugger collections
  debug.rs               — debugger policy, stops, initializer suppression
  fetch.rs               — trusted instruction fetch/decode
  safepoint.rs           — bounded cancellation, task yield, and host polling

crates/fpas-vm/src/vm/operations/
  integer.rs             — direct typed integer handlers
  real.rs                — direct typed real handlers
  dynamic.rs             — generic slow path only where required
  calls.rs               — verified frame transition fast path

crates/fpas-std/src/dispatch/
  mod.rs                 — direct Intrinsic family dispatch
  hosted.rs              — explicit VM-owned classification

This is a planning layout, not a requirement to preserve existing files. The key ownership rule is that debugger state belongs to execution/debug.rs, not to every normal Worker instruction.

Staged work with exit gates

Stage 0 — Establish a current profile

  • Save the full suite baseline.
  • Profile the five audit workloads and capture allocation evidence.
  • Add an instruction-family counter outside timed production runs if sampling cannot distinguish handlers.

Exit gate: current inclusive/self-time evidence names the top three runtime costs; no implementation starts from historical timing alone.

Stage 1 — Split fast and debug execution policies

Move initializer suppression, data-breakpoint tracking, debug task clocks, and debugger-only stop logic into a debug executor. The normal executor should not own or scan those collections. Shared instruction semantics can be generated from one internal opcode definition or factored into cold helpers, but the hot loops themselves should remain independently optimizable.

A safe first design uses monomorphized policy types or two concrete loops. Avoid one if debugging inside every iteration.

Exit gate: all debugger tests pass; normal VM geometric mean improves reproducibly; no benchmark row regresses beyond the agreed threshold. Otherwise revert.

Stage 2 — Trust verified code once

Convert admitted bytecode into a private execution image whose instruction addresses, opcode forms, register windows, branch targets, call arities, constant references, and layout references are already proven. Keep detailed validation at load/link time. In the hot loop use infallible internal register IDs and direct payload decoding.

Keep memory safety without immediately introducing unsafe: safe indexing and compact internal newtypes can remove error construction and repeated conversions first. If bounds checks remain measurable later, isolate any unchecked access in one tiny audited module backed by verifier fuzzing.

Exit gate: malformed artifacts are still rejected before execution; verifier/property tests cover every trusted invariant; profiles show reduced dispatch self time.

Stage 3 — Execute typed opcodes directly

AddInteger should read two integer slots, perform the operation, and write an integer slot. It should not clone two generic values, route through BinaryOperation, and rediscover both tags. Keep *Dynamic opcodes on the generic slow path. Add direct comparison and branch forms as profiles justify them.

Candidate superinstructions include common counted-loop steps, compare-and-branch, load-field-and-use, and call/return patterns. Lua's integer FORLOOP is evidence that fusing language-neutral runtime work can pay without changing source syntax.

Exit gate: integer and branch rows improve, dynamic behavior remains correct, bytecode-size and compile-time changes are recorded, and the full suite has no collateral loss.

Stage 4 — Replace router chains with direct intrinsic dispatch

Dispatch directly on the top-level Intrinsic family and call exactly one owning module. Encode “hosted”, “suspending”, and “callback” ownership as generated metadata beside the intrinsic declaration instead of repeating large matches! lists across crates. This centralizes the invariant and removes up to 16 indirect probes.

Specialize tiny pure intrinsics such as array/string length at the VM seam only if the direct router remains visible in profiles.

Exit gate: intrinsic ownership has one source of truth; array/string length and TUI improve; all intrinsic coverage tests still prove complete routing.

Stage 5 — Deepen calls and callbacks

Resolve callback target, visible arity, capture count, and task ownership when a function value is created or when a higher-order operation begins, not for every element. Run synchronous callbacks as ordinary frames on the current worker where re-entrancy permits, instead of resetting a nested worker per element. Preallocate result capacity for Map and known-size transforms.

Exit gate: callback throughput improves materially, recursive callbacks and hosted re-entrancy remain correct, and spawned-task suspension semantics are unchanged.

Stage 6 — Specialize globals and safepoints

Use an unlocked global store while the VM is provably single-worker. Promote to shared storage before the first parallel task can observe it, or place synchronization at task scheduling/safepoints rather than every access. Poll cancellation and debug traps at bounded safepoints—calls, returns, backward branches, intrinsic transitions, and a countdown—rather than running all control checks per instruction.

Exit gate: global access improves, the task row does not regress, data races remain impossible under Loom/model tests or equivalent stress tests, and cancellation latency stays bounded.

Expected order of leverage

  1. Execution-policy split and trusted execution image.
  2. Direct typed scalar handlers.
  3. Direct intrinsic family routing.
  4. Callback frames on the current worker.
  5. Single-worker globals and explicit safepoints.
  6. Only then reconsider bytecode width, managed heap, or native compilation.

Risks

  • Duplicating fast/debug loops can drift. Generate shared opcode coverage and test both executors against the same corpus.
  • Moving checks to verification increases the verifier's security responsibility. Fuzz and mutation-test artifact admission.
  • Superinstructions can bloat code and harm instruction-cache locality. Add only profile-backed combinations.
  • Inlining every operation can make the dispatch function too large. Keep rare operations cold and profile code layout.
  • Global-store specialization must preserve the current concurrency semantics exactly.
This plan intentionally stops at architecture and gates. No speedup is claimed until measured with cargo bench-fpas. For larger replacement choices, see runtime rewrite options.
