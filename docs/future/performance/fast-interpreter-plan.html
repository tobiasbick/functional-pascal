Recover a fast interpreter before replacing it

The first solution is a staged interpreter cleanup that preserves FPAS behavior and the verified register bytecode. It targets costs already present at instruction, call, intrinsic, and global-access frequency. Every stage has its own rollback point.

Current recommendation: retain the six accepted interpreter changes and the separately measured bounded managed buffer heap. The heap improved both end-to-end TUI workloads by about 7% without changing interpreter dispatch, bytecode, or FPAS behavior. The remaining bounded interpreter candidates were measured and removed. No incremental interpreter item remains open; a full handle/tracing heap still requires new evidence about costs left after buffer reuse.

The normal dispatcher now uses a statically specialized path without debugger initializer suppression. Debugger-owned task execution selects the corresponding debug specialization. Both paths share the same Rust opcode implementation, so there is no runtime if debugging in normal execution and no duplicated source-level opcode match.

Stage 2 result — bounded trusted execution probes

The safe incremental version of a trusted execution image was tested in two additional one-variable designs. The first stored one verifier-built opcode per packed instruction and fetched both by the same instruction index. The second kept packed decoding unchanged but trusted the verified portable instruction range for address conversion, code fetch, and IP increment. Both designs exercised the production VM and automatically followed debugger live-image replacement because the prepared data belonged to the verified image or current worker.

Unexpected operand tags still fall back to the generic path so malformed-bytecode diagnostics do not change.

Stage 3c result — direct typed-real arithmetic

A dedicated 20-million-iteration loop exercised three statically typed real operations per iteration. The candidate split AddReal, SubtractReal, MultiplyReal, DivideReal, and NegateReal from the generic numeric router while preserving its fallback diagnostics and division-by-zero behavior.

The complete VM-group comparison moved real_loop from 3058 to 3035 ms (−0.8%). Other rows remained below the 5% regression gate, but the target gain was far below the improvement gate. The direct handlers, pure real-operation module, diagnostic test, temporary benchmark, and suite entry were all removed. Real comparison opcodes remain independent because Stage 3b showed a 10.2–12.8% comparison gain versus only 2.9–3.0% for integer arithmetic.

Stage 3d result — direct typed-real comparisons

A second isolated benchmark alternated two real operands and executed equality, inequality, and all four ordering relations on every iteration: 18 million typed comparisons per measured run. The candidate bypassed generic aggregate-aware comparison routing for verified real operands while preserving malformed-image fallback and the existing NaN diagnostic.

The complete VM-group comparison moved real_comparison from 1584 to 1576 ms (−0.5%). No other row crossed the 5% regression gate, but the target result was negligible. The handler, NaN regression test, temporary benchmark, and suite entry were removed. Together with Stage 3c, this closes typed-real specialization without an accepted runtime change.

Stage 3e result — normal-run compare/branch fusion

The frequency gate passed: branch_dispatch emits one adjacent integer comparison and branch for its parity test and another for its loop condition, yielding roughly 40 million dynamic pairs. The bounded prototype recognized all six integer comparison opcodes followed by BranchIfFalse or BranchIfTrue on the comparison destination. It fused only scheduler-free normal execution, retained the Boolean register result and two-instruction accounting, and left tasks, debugger execution, and cancellable runs unchanged.

The complete VM-group comparison slowed branch_dispatch from 3147 to 3258 ms (+3.5%). The extra look-ahead and eligibility branches cost more than the avoided dispatch. The fusion module, shared comparison primitive, and regression test were removed. No narrower superinstruction remains justified; a redesigned compact instruction encoding belongs to deferred Option A and must satisfy that option's profile and production-prototype gates.

Stage 4 result — direct intrinsic ownership routing

Each intrinsic now has one bytecode-owned execution classification: standard-library, VM-hosted, callback, or task. The VM selects that owner once. Hosted operations dispatch directly to their family, while fpas-std uses one top-level family match instead of probing 16 function pointers. Mutable task and sleep handling is derived from the same classification seam.

Design target

Small interface

run_until_event(), resume(), and state inspection only through an explicit debug adapter.

Deep implementation

Instruction fetch, frame transitions, safepoints, task yielding, diagnostics, counters, and debug hooks stay behind the execution seam.

Two real adapters

A normal fast executor and a debugger executor justify the seam. Normal execution must not branch on debug state for every instruction.

Proposed module shape

crates/fpas-vm/src/vm/execution/
  mod.rs                 — narrow run/resume interface and shared outcomes
  fast.rs                — normal execution loop; no debugger collections
  debug.rs               — debugger policy, stops, initializer suppression
  fetch.rs               — trusted instruction fetch/decode
  safepoint.rs           — bounded cancellation, task yield, and host polling

crates/fpas-vm/src/vm/operations/
  integer.rs             — direct typed integer handlers
  real.rs                — direct typed real handlers
  dynamic.rs             — generic slow path only where required
  calls.rs               — verified frame transition fast path

crates/fpas-std/src/dispatch/
  mod.rs                 — direct Intrinsic family dispatch
  hosted.rs              — explicit VM-owned classification

This is a planning layout, not a requirement to preserve existing files. The key ownership rule is that debugger state belongs to execution/debug.rs, not to every normal Worker instruction.

Stage 1 — Split fast and debug execution policies

Move initializer suppression, data-breakpoint tracking, debug task clocks, and debugger-only stop logic into a debug executor. The normal executor should not own or scan those collections. Shared instruction semantics can be generated from one internal opcode definition or factored into cold helpers, but the hot loops themselves should remain independently optimizable.

A safe first design uses monomorphized policy types or two concrete loops. Avoid one if debugging inside every iteration.

Status: complete on 30 August 2026. The complete fpas-vm suite passed, the VM improvements repeated, and the full-suite follow-up found no stable collateral regression.

Stage 2 — Trust verified code once

Convert admitted bytecode into a private execution image whose instruction addresses, opcode forms, register windows, branch targets, call arities, constant references, and layout references are already proven. Keep detailed validation at load/link time. In the hot loop use infallible internal register IDs and direct payload decoding.

Keep memory safety without immediately introducing unsafe: safe indexing and compact internal newtypes can remove error construction and repeated conversions first. If bounds checks remain measurable later, isolate any unchecked access in one tiny audited module backed by verifier fuzzing.

Status: bounded safe slice rejected on 30 August 2026. Trusted branch targets, a predecoded opcode mirror, and an infallible fetch path all missed the broad 5% gate and were rolled back. A wider compact, typed, or quickened instruction image is deferred to runtime-rewrite Option A; it is not an unfinished incremental Stage-2 patch.

Stage 3 — Execute typed opcodes directly

AddInteger now reads two integer values, performs the operation through a shared integer primitive, and writes the result without passing through the generic operation router. Stage 3a removed generic source-value cloning; Stage 3b specialized typed integer arithmetic, comparisons, bitwise operations, and shifts. *Dynamic opcodes remain on the generic slow path. Stage 3c found only a 0.8% gain from direct typed-real arithmetic; Stage 3d found only 0.5% for direct typed-real comparisons; Stage 3e slowed the high-frequency branch workload by 3.5% with normal-run pair fusion. All three were removed.

Counted-loop steps, compare-and-branch, load-field-and-use, and call/return were considered as possible superinstructions. The highest-frequency bounded form, compare-and-branch, was slower. The others have no profile-backed frequency or cost evidence and are therefore deferred with compact instruction design rather than left as an implementation backlog. Lua's integer FORLOOP remains useful external evidence, not proof that the same tradeoff wins in FPAS.

Status: Stages 3a and 3b completed on 30 August 2026; Stages 3c, 3d, and 3e rejected on 4 September 2026. Direct integer comparisons improved the branch workload by 10.2–12.8%; the arithmetic loop improved by 2.9–3.0%. The complete VM suite passed, including aliasing and integer-domain edges, and the full-suite follow-up had no collateral regression. Typed-real and bounded superinstruction work are closed.

Stage 4 — Replace router chains with direct intrinsic dispatch

Dispatch now starts from the top-level Intrinsic family and calls exactly one owning subsystem. Standard, hosted, callback, task, and mutable-dispatch classification lives beside the intrinsic declaration instead of being repeated as large matches! lists across crates. This centralizes the invariant and removes up to 16 indirect probes.

Tiny pure intrinsics did not need VM-specific fast paths: direct family routing alone produced the measured gain.

Status: complete on 30 August 2026. Intrinsic dispatch improved by 14.0–14.1%, array length by 14.1–15.3%, and string length by 8.8–10.0%. No full-suite row crossed the 5% regression gate, and ownership coverage has one source of truth with exhaustive tests.

Stage 5 — Deepen calls and callbacks

The first accepted slice removed the temporary argument buffer from cached worker resets while preserving receiver, argument, capture, and task-owner ordering. A standalone attempt to resolve callback metadata once per higher-order operation did not help and was rolled back. Stage 5b then tested ordinary frames on the current worker. Reusing the task-continuation machinery was initially 76.0% slower and remained 21.5% slower after removing its per-call argument allocation and full array copy. A separate direct synchronous frame loop was 41.4% slower. Exact result-capacity preallocation for task-owned Array.Map later produced only a 1.0% longer-run median gain. All failed variants were rolled back.

Status: Stage 5a complete; Stage 5b rejected on 30 August 2026; result-capacity preallocation rejected on 4 September 2026. Stage 5a retains its repeatable 23.9–24.1% array_callbacks improvement and regression test for reused bound receivers. The cached nested worker remains because the alternatives failed the improvement gate without providing a compensating semantic benefit.

Stage 6 — Specialize globals and safepoints

Stage 6a now selects worker-owned slots only for normal runs whose verified image has neither task-spawning functions nor callback-owned intrinsics. Task pools, callback sessions, callback intrinsics, direct callback entry, and debugger sessions keep the existing shared RwLock storage. The local vector never crosses a worker boundary, so no promotion protocol or unsafe synchronization was needed. Global mutability, initialization, indexed replacement, diagnostics, and FPAS semantics remain unchanged.

The initial forward comparisons moved global_access from 649 ms to 499/508 ms, but unrelated rows also showed machine drift. A stricter back-to-back reverse A/B saved Local at 485 ms, disabled only the Local selector, and measured Shared at 554 ms (+14.2%); restoring Local returned the row to 508 ms. Callback and task programs remained on Shared. All 384 VM tests, including debugger, task, callback, cancellation, global mutation, and indexed-global cases, passed.

Stage 6b tested the remaining cancellation-check hypothesis on 4 September 2026. The candidate attached the scheduler only to task-capable execution, retained shutdown handles, or an already-cancelled VM, then selected statically specialized polling and no-poll root loops. Task execution and debugger dispatch remained unchanged. A forward suite comparison was noisy, so a stricter reverse A/B compared the same restructured code with polling forced back on. Median polling-to-no-poll results were integer_loop 6566→6601 ms (+0.5%), branch_dispatch 3161→3257 ms (+3.0%), function_call 699→686 ms (−1.9%), and intrinsic_dispatch 1766→1793 ms (+1.5%).

The candidate missed the 5% gate and was slower in three of four repeated workloads. It was rolled back completely, including the loop split and scheduler-selection tests. The current exact instruction-boundary cancellation behavior remains intact. The earlier fixed-cadence scheduler-poll probe also remains rejected because it regressed the branch workload.

Status: Stage 6a complete on 30 August 2026; Stage 6b measured and rejected on 4 September 2026. Re-entry gate: a new profile must identify material cancellation-check self-time that neither rejected probe measured.

Risks

  • Duplicating fast/debug loops can drift. Generate shared opcode coverage and test both executors against the same corpus.
  • Moving checks to verification increases the verifier's security responsibility. Fuzz and mutation-test artifact admission.
  • Superinstructions can bloat code and harm instruction-cache locality. Add only profile-backed combinations.
  • Inlining every operation can make the dispatch function too large. Keep rare operations cold and profile code layout.
  • Global-store specialization must preserve the current concurrency semantics exactly.
