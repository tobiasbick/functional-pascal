Ranked hot-path findings

Priority 1 · high confidence

Normal execution pays debugger bookkeeping on every instruction

vm/dispatch.rs performs callback-continuation checks, address conversion, code bounds checks, checked IP and instruction-counter increments, and opcode validation before reaching the opcode match. Initializer suppression now uses a statically selected debugger specialization, so normal execution does not perform that debugger-only lookup.

Why it matters: a 50-million-iteration loop executes several bytecodes per iteration. Nanoseconds added to every bytecode become seconds. The broad regression shape is consistent with common dispatch overhead.

Status: the controlled execution-policy split produced a small repeatable improvement but did not explain most of the broad historical regression.

Priority 2 · confirmed hot path

Typed opcodes still execute through generic Value machinery

The bytecode distinguishes AddInteger, AddReal, and AddDynamic. execute/scalar.rs now borrows source values instead of cloning them, but typed opcodes still route through BinaryOperation. value_ops/scalar.rs:36–84 then branches on the abstract operation and rediscovers runtime tags. Register IDs, reads, and writes remain fallible after executable verification.

Measured evidence: borrowing operands improved integer_loop by 9.9–11.3%, branch_dispatch by 9.4–10.1%, and dynamic_numeric by 6.3–7.5% in two full-suite comparisons. Direct typed handlers remain the next hypothesis.

Priority 3 · high confidence

Higher-order array operations cross an expensive callback seam per element

callback_call.rs:13–155 resolves and revalidates the callback, clones a SharedFunction, collects a new argument vector, borrows a RefCell, resets a nested Worker, copies arguments/captures, runs a second dispatch loop, and returns the worker to the cache. callbacks/synchronous.rs:28–131 repeats that for every Map, Filter, and Reduce element.

Evidence: array_callbacks is the largest regression (+79.4%). Its workload performs 9.6 million callbacks, so even small fixed callback costs dominate.

Priority 4 · strong static candidate

Intrinsic dispatch is a chain of routers and indirect function calls

Every intrinsic first visits up to six hosted routers in hosted/mod.rs:33–57. A non-hosted intrinsic then enters fpas-std/intrinsics.rs:52–229, checks several large “VM-only” classifiers, and iterates over 16 function pointers until a unit accepts it. This prevents a simple direct top-level enum dispatch and can inhibit inlining.

Signal: array_length and cached string_length do almost no useful work yet are 26.7% and 30.9% slower than the earlier record. That makes surrounding routing disproportionately important. A profile is still required to quantify it.

Priority 5 · confirmed mechanism

Copy-on-write preserves semantics but turns many updates into heap work

Value stores strings, arrays, records, enums, dictionaries, and functions behind Arc. Cloning is cheap until mutation; value/aggregate.rs:29–49 and value/array.rs:7–43 use Arc::make_mut, which detaches shared bodies. execute/aggregates.rs:201–223 clones a record before each with update and then mutates through the COW body.

Existing evidence: prior native profiling named value drop and aggregate traversal. This is also a structural explanation for TUI workloads that continually construct and discard immutable trees.

Priority 6 · confirmed mechanism

Every global read and write locks the entire global vector

execute/aggregates.rs:15–60 takes an RwLock for every global load/store, clones values, and checks mutability and initialization at runtime. The lock is necessary for the current cross-task representation, but it is paid by the common single-root-task case too.

Signal: the dedicated global benchmark is 34.9% slower than 10 August. This mechanism is certainly exercised; its percentage share needs sampling or an isolated A/B design.

Priority 7 · known non-runtime cost

Multi-program tests still repeat program parsing and compile/link work

The measured TUI-test bottleneck was repeated parsing of 120 standard-library sources and unit-graph construction. ProgramUnitGraph now reuses that graph and reduced the warm FPAS TUI group from 53.20 s to about 37.8 s. However, project_build.rs:103–120 still parses, resolves, builds, verifies, and links each program independently. This is a separate startup/test-throughput problem, not part of the in-program benchmark timer.

What the existing profile already ruled down

The accepted register-VM investigation measured a 43-element TUI view tree at only 11–12 ms for 500 builds, below 0.4% of the then 3,458 ms render workload. It also showed that reusable register storage removed the earlier Vec<Value>::resize/extend_with call-profile bottleneck. Repeating those optimizations first would ignore the newer evidence.

Measurement protocol and completed probes

  1. Current VM and full-suite baselines were saved with the project harness.
  2. Windows sampling was attempted, but samply required administrator privileges; no system configuration was changed.
  3. One-variable A/B probes covered debug-policy separation, branch-target revalidation, forced dispatch inlining, scheduler polling cadence, and scalar operand cloning.
  4. The complete suite was compared twice for the accepted operand-borrowing change; variants below the improvement gate or with regressions were rolled back.
  5. Add microbenchmarks only for a hotspot that the end-to-end suite cannot isolate; keep end-to-end rows authoritative.

Audit limits

  • No fresh sampling profile was captured, so this report does not assign CPU percentages to current functions.
  • Historical records can drift with compiler, hardware load, and unrelated code. Only controlled before/after comparisons can establish a win.
  • Source inspection can identify frequency and allocation mechanisms, but not whether LLVM already optimized a check away.
  • The reports deliberately avoid syntax or semantic changes.
