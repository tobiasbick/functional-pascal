Original ranked findings, with current status

The priority numbers preserve the original investigation order. They are not a current CPU ranking; use the next-work table for the current order.

Priority 1 · debugger lookup addressed and measured

Normal execution no longer performs debugger initializer lookup

vm/dispatch.rs performs callback-continuation checks, address conversion, code bounds checks, checked IP and instruction-counter increments, and opcode validation before reaching the opcode match. Initializer suppression now uses a statically selected debugger specialization, so normal execution does not perform that debugger-only lookup.

Why it matters: a 50-million-iteration loop executes several bytecodes per iteration. Nanoseconds added to every bytecode become seconds. The original broad regression shape was consistent with common dispatch overhead; current remaining costs need fresh attribution.

Status: the controlled execution-policy split produced a small repeatable improvement but did not explain most of the broad historical regression. Later trusted branch-target, opcode-mirror, and infallible-fetch probes also missed the broad 5% gate and were rolled back; a wider compact instruction image is deferred rather than an open cleanup.

Priority 2 · confirmed hot path

Typed integer opcodes now bypass generic Value routing

The bytecode distinguishes AddInteger, AddReal, and AddDynamic. execute/integer.rs now handles typed integer arithmetic, bitwise, shift, and comparison opcodes directly, while value_ops/integer.rs keeps their pure semantics shared with generic evaluation. Typed real opcodes and register reads remain generic and fallible after executable verification.

Measured evidence: direct integer handling improved branch_dispatch by 10.2–12.8% and integer_loop by 2.9–3.0% in two VM comparisons. Together with borrowed operands, the full-suite follow-up measured cumulative improvements of 17.8% and 9.5% respectively, with no collateral regression. An isolated real loop moved from 3058 to 3035 ms (−0.8%) with direct typed-real arithmetic. A second benchmark executed all six typed-real comparisons 18 million times and moved from 1584 to 1576 ms (−0.5%). Both candidates and temporary benchmarks were removed; typed-real specialization is closed without an accepted change.

Priority 3 · cached path improved; frame replacement rejected

Higher-order array operations still cross a callback seam per element

callback_call.rs still resolves and revalidates the callback, clones a SharedFunction, borrows a RefCell, resets a nested Worker, copies values into registers, runs a second dispatch loop, and returns the worker to the cache. The cached reset no longer collects an intermediate argument vector: it loads the optional receiver, visible arguments, and captures directly. callbacks/synchronous.rs repeats the remaining seam for every Map, Filter, and Reduce element.

Measured evidence: removing the per-callback argument allocation improved array_callbacks by 24.1% and 23.9% in two full-suite comparisons. The workload performs 9.6 million callbacks, so small fixed costs dominate. Caching callback resolution alone was slower by 1.7% and 3.6%. An allocation-free current-worker continuation was 21.5% slower, and a direct synchronous frame loop was 41.4% slower. Exact result-capacity preallocation for task-owned Array.Map initially measured −5.8%, but a longer reverse A/B reduced the median from 3014 to 2983 ms, only −1.0%. These alternatives were rolled back; the cached nested worker remains the measured synchronous fast path. A later distinct change uses inline task-callback arguments and improved its production workload by 17.5%; see the allocation follow-up.

Priority 4 · addressed and measured

Intrinsic dispatch no longer probes router chains

intrinsic/execution.rs now assigns each intrinsic to its standard-library, VM-hosted, callback, or task owner. execute/intrinsics.rs selects that owner once; hosted and standard operations then use a direct top-level family match instead of visiting six hosted routers and up to 16 standard-library function pointers.

Measured result: the new mixed intrinsic_dispatch benchmark improved by 14.0–14.1% in two full-suite comparisons. array_length improved by 14.1–15.3% and string_length by 8.8–10.0%, with no row crossing the 5% regression gate. Length-specific VM fast paths were unnecessary.

Priority 5 · confirmed mechanism

Copy-on-write preserves semantics but turns many updates into heap work

Value stores strings, arrays, records, enums, dictionaries, and functions behind Arc. Cloning is cheap until mutation; value/aggregate.rs and value/array.rs use Arc::make_mut, which detaches shared bodies. execute/aggregates.rs clones a record before each with update and then mutates through the COW body.

Measured follow-up: bounded backing-buffer reuse improved the two TUI workloads by about 7%; wrapper-payload pooling later improved its focused workload by 31.2%. Temporary DHAT instrumentation attributed 37.5% of allocation events in each TUI workload to selected remaining Record/string body sites. That is an event share, not CPU time. A synchronized Record-slot prototype then regressed TUI by 96.6% and Notes by 33.4% and was removed. The remaining ownership mechanism is real, but does not justify a full-heap rewrite without new CPU attribution.

Priority 6 · addressed and measured

Eligible normal runs no longer lock the global vector

vm/globals.rs selects worker-owned slots for verified normal images without task-spawning functions or callback-owned intrinsics. execute/aggregates.rs and the indexed-global update path use that local vector without locking. Debugger, task, callback-session, and callback-intrinsic execution retain the shared RwLock representation.

Measured result: a back-to-back reverse A/B saved Local at 485 ms and measured Shared at 554 ms (+14.2%); restoring Local produced 508 ms. Three task measurements overlapped recent history rather than showing a stable regression, and all VM task/callback/debugger tests passed.

Priority 7 · measured and rejected

Per-instruction cancellation polling is not a material normal-run bottleneck

vm/worker.rs checks scheduler cancellation at each root instruction boundary. Stage 6b tested a statically specialized no-poll loop for normal runs without tasks or a retained shutdown handle while preserving polling for task-capable, cancelled, and externally controlled execution.

Measured result: reverse A/B medians for polling-to-no-poll were integer_loop 6566→6601 ms (+0.5%), branch_dispatch 3161→3257 ms (+3.0%), function_call 699→686 ms (−1.9%), and intrinsic_dispatch 1766→1793 ms (+1.5%). The candidate was slower in three workloads, missed the 5% gate, and was removed. Exact instruction-boundary cancellation remains.

Priority 8 · measured and rejected

Runtime compare/branch look-ahead costs more than a second dispatch

The existing branch_dispatch workload executes an integer comparison followed immediately by a conditional branch for both its parity test and loop condition: roughly 40 million dynamic candidate pairs. A prototype recognized all six integer comparison opcodes followed by a branch on their destination register, but only in scheduler-free normal execution. It preserved the Boolean register result and logical instruction count; task, debugger, and cancellable paths remained unchanged.

Measured result: the complete VM comparison slowed branch_dispatch from 3147 to 3258 ms (+3.5%). No row crossed the 5% regression threshold, but the target moved in the wrong direction. The look-ahead handler and regression test were removed. Wider fused bytecode is not an incremental follow-up; it belongs to deferred compact-VM Option A.

Priority 9 · known non-runtime cost

Multi-program tests still repeat program parsing and compile/link work

The historical TUI-test investigation found repeated parsing of 120 standard-library sources and unit-graph construction; graph reuse reduced that warm group from 53.20 s to about 37.8 s at the time. Those counts and timings are not a current inventory or baseline. build_test_program_with_graph still parses and prepares each root program, but unit builds can reuse compatible .fpascu sidecars and program artifacts can reuse compatible .fpascp images before linking. Measure cold/warm phase time and reuse hits for the complete group before adding caching. The new compiler_lowering benchmark covers semantic analysis and IR lowering only; it does not close this startup/test-throughput gap.

What the existing profile already ruled down

The accepted register-VM investigation measured a 43-element TUI view tree at only 11–12 ms for 500 builds, below 0.4% of the then 3,458 ms render workload. It also showed that reusable register storage removed the earlier Vec<Value>::resize/extend_with call-profile bottleneck. Repeating those optimizations first would ignore the newer evidence.

Measurement protocol and completed probes

  1. Current VM and full-suite baselines were saved with the project harness.
  2. Windows sampling was attempted, but samply required administrator privileges; no system configuration was changed.
  3. One-variable A/B probes covered debug-policy separation, branch-target revalidation, forced dispatch inlining, scheduler polling cadence, scalar operand cloning, direct typed integer handling, direct intrinsic ownership routing, callback preparation caching, and cached callback argument loading.
  4. The complete suite was compared twice for accepted operand-borrowing, intrinsic-routing, and callback-loading changes; variants below the improvement gate or with regressions were rolled back.
  5. Add microbenchmarks only for a hotspot that the end-to-end suite cannot isolate; keep end-to-end rows authoritative.

Audit limits

  • No fresh CPU sampling profile was captured in this review, so this report does not assign CPU percentages to current functions. Later DHAT allocation counts are documented separately and are not CPU samples.
  • Historical records can drift with compiler, hardware load, and unrelated code. Only controlled before/after comparisons can establish a win.
  • Source inspection can identify frequency and allocation mechanisms, but not whether LLVM already optimized a check away.
  • The reports deliberately avoid syntax or semantic changes.
