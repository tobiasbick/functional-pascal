A bounded managed heap helps FPAS

The experiment retains FPAS value semantics and the existing bytecode while reusing aggregate buffers, strings, and small wrapper boxes on the thread that releases them. Repeated A/B measurements show material gains in end-to-end and focused production workloads, so the successful layers are retained.

Decision: retain. The fresh A/B median improved tui_headless by 7.0% and notes_headless by 7.2%. Record-heavy microbenchmarks improved by roughly 14%, and string concatenation by roughly 6%. No long-running guard workload showed a repeatable regression.

What “managed heap” means here

A managed heap is runtime-owned storage for dynamically allocated values. Instead of asking the system allocator to create and destroy every array, record, string, or object independently, the runtime controls allocation and reclamation. Large VMs often combine compact handles or tagged slots with tracing garbage collection. Region systems instead free many short-lived objects together.

This experiment deliberately tests a smaller production seam first. FPAS still stores aggregate bodies behind Arc and preserves copy-on-write behavior. When the final array, record, enum, dictionary, or string owner disappears, an eligible cleared buffer enters a bounded thread-local pool. A later aggregate construction can take that buffer without another allocator round trip.

FPAS Value (unchanged 16-byte ceiling)
  ├─ Arc/COW body (unchanged ownership semantics)
  │    ├─ Vec<Value>          arrays, records, enums
  │    ├─ Vec<(Value,Value)> dictionaries
  │    └─ String              UTF-8 payloads
  └─ uniquely owned Box<Value>  Result/Option payloads
               ↓ final owner drops
       bounded thread-local storage pools
               ↓ next matching construction
       cleared storage reused
Not a tracing garbage collector: this does not introduce handles, root maps, safepoints, barriers, cycle collection, object movement, or stop-the-world pauses. Atomic Arc reference counts and one small body allocation per shared object remain. “Managed heap” in this report means a bounded runtime-managed reuse layer.

Correctness and implementation finding

The first pool version found an important destruction-order hazard: it cleared nested Values while holding a mutable borrow of the thread-local pool. Dropping a nested aggregate could re-enter the same pool and abort the process. The final design takes and clears the buffer before borrowing the pool, and uses fallible thread-local access during thread shutdown. Regression tests cover clearing and reuse, oversized-buffer rejection, string reuse, and recycling on the thread that performs the final drop.

  • FPAS syntax, semantics, bytecode, value-size ceiling, debugger protocol, and artifact format are unchanged.
  • Copy-on-write tests for arrays, records, enums, and dictionaries continue to pass.
  • The retained implementation is covered by the successful workspace verification through 77fac915. This documentation review adds no code and did not rerun the suite.

What this result does and does not justify

The result proves that allocator traffic and backing-buffer destruction were material in the measured aggregate and TUI paths. It justifies retaining this bounded layer. It does not prove that replacing every Arc with handles and adding a tracing collector would provide a proportional gain: the accepted layer already removes part of that cost, while a collector would add root tracking, safepoints, barriers, task-sharing policy, debugger integration, and pause behavior.

A full tagged-slot or tracing heap remains deferred. Later DHAT profiles justified investigating remaining body allocations, but allocation-event counts do not satisfy the major-rewrite gate of at least 25% of target CPU time. The synchronized reusable-slot prototype also failed the runtime comparison badly. Re-enter the design only with a VM-owned arena that can provide stable handles and safepoint reclamation without a lock on every value access, and still require wins in at least two end-to-end workloads without regressing startup or tasks.

Follow-up allocation experiments

All five experiments below are complete: two accepted and three rejected. Each was evaluated separately; accepted implementations required a reproducible affected-workload improvement of roughly 5% or more without a material regression elsewhere. The table is an outcome ledger, not an open implementation queue. Rejected results remain here so the same designs are not repeated without new evidence.

4Store small records and enums inline, or otherwise remove their remaining body allocation.Rejected; implementation revertedThe prototype stored zero to four fields directly in each record or enum body and kept larger aggregates in the existing managed vector pool. Against the accepted reuse-heap baseline, record_field_access changed from 1484 to 1500 ms (+1.1%) and record_update from 378 to 363 ms (−4.0%), so neither affected benchmark cleared the 5% gate. It also measured slower in array_callbacks (+8.9%), TUI (+3.3%), and Notes (+4.2%). Enlarging every aggregate body outweighed the removed small-vector indirection, so the implementation and its tests were removed.
5Prototype a handle, tracing, or epoch heap only if remaining allocation evidence clears the design gate.Rejected; prototype revertedTemporary DHAT profiles found 15,427,822 allocation events in TUI and 26,563,598 in Notes. The explicit SharedRecord::new and SharedStr::from(&str) body sites alone contributed 5,785,494 (37.5%) and 9,952,478 (37.5%) events respectively, which justified a bounded investigation of body allocation; these counts do not establish its CPU-time share. A production-path reusable Record slot then removed repeated body allocation while preserving FPAS value semantics and the existing Value size. Its synchronized body access changed record_field_access from 1484 to 2005 ms (+35.1%), record_update from 378 to 462 ms (+22.2%), TUI from 3826 to 7521 ms (+96.6%), and Notes from 8161 to 10889 ms (+33.4%). Locks and indirection cost much more than the saved allocation, so all prototype code and profiler instrumentation were removed. A future collector must use VM-owned stable handles and safepoints rather than globally synchronized per-object slots.

Conditional refinements, not queued work

No allocation experiment above remains open. The Substring follow-up has measured gains; project-aware LSP measurement is next; full-heap work stays behind the major-rewrite gates.

  1. Add low-overhead benchmark-only pool counters only when tuning pool bounds or investigating a concrete workload regression.
  2. Do not retry synchronized per-object slots: their measured access cost dominates the allocator saving.
  3. If collection is revisited, make the heap VM-owned and resolve stable handles without a global lock; reclaim only at explicit VM safepoints.
  4. Require the replacement to beat the retained buffer pools in at least two end-to-end workloads before expanding it to all value types.
