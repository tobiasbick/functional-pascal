A bounded managed heap helps FPAS

The experiment retains FPAS value semantics and the existing bytecode while reusing aggregate buffers, strings, and small wrapper boxes on the thread that releases them. Repeated A/B measurements show material gains in end-to-end and focused production workloads, so the successful layers are retained.

Decision: retain. The fresh A/B median improved tui_headless by 7.0% and notes_headless by 7.2%. Record-heavy microbenchmarks improved by roughly 14%, and string concatenation by roughly 6%. No long-running guard workload showed a repeatable regression.

What “managed heap” means here

A managed heap is runtime-owned storage for dynamically allocated values. Instead of asking the system allocator to create and destroy every array, record, string, or object independently, the runtime controls allocation and reclamation. Large VMs often combine compact handles or tagged slots with tracing garbage collection. Region systems instead free many short-lived objects together.

This experiment deliberately tests a smaller production seam first. FPAS still stores aggregate bodies behind Arc and preserves copy-on-write behavior. When the final array, record, enum, dictionary, or string owner disappears, an eligible cleared buffer enters a bounded thread-local pool. A later aggregate construction can take that buffer without another allocator round trip.

FPAS Value (unchanged 16-byte ceiling)
  └─ Arc/COW body (unchanged ownership semantics)
       ├─ Vec<Value>          arrays, records, enums
       ├─ Vec<(Value,Value)> dictionaries
       ├─ String              UTF-8 payloads
       └─ Box<Value>          Result/Option payloads
             ↓ final owner drops
       bounded thread-local capacity buckets
             ↓ next matching construction
       cleared buffer reused
Not a tracing garbage collector: this does not introduce handles, root maps, safepoints, barriers, cycle collection, object movement, or stop-the-world pauses. Atomic Arc reference counts and one small body allocation per shared object remain. “Managed heap” in this report means a bounded runtime-managed reuse layer.

Benchmark method and evidence

The first complete baseline run was cold and visibly inconsistent with later TUI measurements, so it was not used. The saved baseline was replaced with a stable warm full-suite run. The candidate was then measured twice, stashed completely, the unchanged HEAD was rebuilt and measured twice, and the exact candidate was restored, rebuilt, and measured twice more. Correctness and implementation finding

The first pool version found an important destruction-order hazard: it cleared nested Values while holding a mutable borrow of the thread-local pool. Dropping a nested aggregate could re-enter the same pool and abort the process. The final design takes and clears the buffer before borrowing the pool, and uses fallible thread-local access during thread shutdown. Regression tests cover clearing and reuse, oversized-buffer rejection, string reuse, and recycling on the thread that performs the final drop.

  • FPAS syntax, semantics, bytecode, value-size ceiling, debugger protocol, and artifact format are unchanged.
  • Copy-on-write tests for arrays, records, enums, and dictionaries continue to pass.
  • The bytecode and VM test suites passed during development; final workspace verification is required by the commit gate.

What this result does and does not justify

The result proves that allocator traffic and backing-buffer destruction were material in the measured aggregate and TUI paths. It justifies retaining this bounded layer. It does not prove that replacing every Arc with handles and adding a tracing collector would provide a proportional gain: the accepted layer already removes part of that cost, while a collector would add root tracking, safepoints, barriers, task-sharing policy, debugger integration, and pause behavior.

A full tagged-slot or tracing heap remains deferred. Re-enter that design only when allocation/self-time evidence attributes at least 25% of a target workload to costs still present after buffer reuse, and when a second production prototype can beat this new baseline in at least two end-to-end workloads without regressing startup or tasks.

Follow-up allocation experiments

The remaining ideas are evaluated one at a time. Each experiment keeps its implementation only when a reproducible affected benchmark improves by roughly 5% or more without a material regression elsewhere. Rejected implementations are removed, but their result remains here so the same path is not repeated without new evidence.

Possible next refinements

  1. Add low-overhead counters in a benchmark-only build to measure pool hit rate, retained bytes, and rejected oversized buffers.
  2. Profile remaining Arc allocation/reference-count and recursive-drop cost after the accepted reuse layer.
  3. If evidence is strong, prototype compact heap handles for one isolated immutable aggregate type before designing collection.
  4. Do not add a collector merely to rename the existing buffer pool; the extra machinery must remove measured remaining cost.
