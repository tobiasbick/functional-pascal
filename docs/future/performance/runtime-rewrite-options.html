If the interpreter is still too slow, replace the right layer

FPAS is free to replace its bytecode and runtime internals. That freedom is valuable only after the common overhead is measured. These options are deliberately more invasive and should compete against a restored fast-interpreter baseline.

Strong recommendation: continue bounded measured interpreter work first. Stage 2 rejected branch-target, opcode-mirror, and fetch optimizations; Stage 5b rejected synchronous callback frames and retained the cached nested worker; Stage 6a accepted worker-local globals; Stage 6b rejected both fixed-cadence and disabled normal-run cancellation polling. Measure known-size result-capacity preallocation next. Keep a compact execution-image rewrite, managed heap, and tiered compilation deferred until their evidence gates are met.

Three options

A · Compact quickened VM

Keep interpretation, replace 64-bit transport instructions with a compact or predecoded runtime format, resolve metadata once, and introduce profile-backed superinstructions.

Cost: medium · Risk: medium · Best near-term rewrite

B · Managed heap runtime

Replace per-value Arc/COW ownership with tagged slots and handles into a VM-owned heap. Use tracing collection or regions to reclaim object graphs in batches.

Cost: high · Risk: high · Best for TUI/aggregate allocation

C · Tiered native execution

Interpret cold code, count method/back-edge heat, compile selected functions or loops from the existing typed IR, and retain interpreter fallback.

Cost: very high · Risk: very high · Highest eventual ceiling

Option A — compact, quickened interpreter

The serialized bytecode can remain portable while loading produces a host-private execution image. The execution image may use 32-bit common instructions, side tables for wide operands, resolved function/layout pointers or indexes, and quickened opcodes such as LoadFieldResolved or CallDirectResolved.

Lua demonstrates the value of compact fixed-width register instructions, specialized immediate/constant arithmetic, inline integer-loop handling, and a minimal fetch path. HotSpot demonstrates resolution caches and rewriting/quickening around an interpreter.

portable artifact
  └─ verify + resolve once
       └─ RuntimeImage
            ├─ compact instruction stream
            ├─ resolved call/layout/intrinsic tables
            ├─ cold source/debug metadata
            └─ immutable verifier proof summary

Advantages

  • Improves instruction-cache density and removes repeated table validation.
  • Keeps startup and implementation complexity far below a JIT.
  • Can preserve the existing Value representation initially.
  • Creates a clean input for later native compilation.

Risks and gates

  • Compact formats need escape instructions or side tables for large programs.
  • Quickening must remain deterministic and debugger/source-map aware.
  • Measure code size, load time, dispatch throughput, and full-suite performance. Reject if gains come only from synthetic loops.

Option B — tagged slots and a VM-owned heap

The current Rust Value is semantically convenient but ownership crosses every operation. Heap objects are independently reference-counted, records and arrays detach under COW mutation, and recursive drops traverse object graphs. A managed runtime can instead make register/global slots small tagged words and keep arrays, strings, records, closures, and variants in one heap.

Scalar moveClone a Rust enum valueCopy one compact tagged slot

Design variants

  1. Tracing generational heap: best general allocation throughput, but requires root maps, barriers, safepoints, and debugger integration.
  2. Reference-counted heap with non-atomic local objects: easier migration; promote objects crossing task boundaries to shared ownership. Complexity moves into promotion and cycles.
  3. Region/arena plus immutable values: allocate per call, frame, or TUI render epoch and reclaim in bulk. Excellent when lifetimes align, awkward for globals, closures, and tasks.
  4. Hybrid: compact slots plus generational tracing for ordinary objects and explicit host handles for resources. This is the strongest long-term model, but the largest rewrite.

FPAS-specific recommendation

Prototype an epoch arena only for one measured allocation-heavy TUI path before committing to a whole-runtime collector. If it proves that aggregate construction/drop dominates, design a compact slot and managed heap together. Do not replace Arc globally based only on aesthetic preference: the earlier compact shared-value change produced major regressions before later optimizations recovered them.

Option C — tiered compilation from typed IR

The repository already has target-independent typed IR, but production execution does not use it. A tiered design can retain the interpreter for startup and debugging, collect cheap counters at method entries and backward branches, then compile only hot functions with Cranelift or another backend.

FPAS source → checked typed IR → portable artifact
                               ├─ interpreter (cold/default)
                               └─ hot-function compiler
                                    ├─ native code cache
                                    ├─ safepoint maps
                                    └─ deopt/fallback metadata

HotSpot's lesson is not “add C2”. It is that interpretation, profiling, baseline compilation, optimized compilation, and deoptimization are separate tiers with different jobs. For FPAS, one interpreter plus one baseline native tier is enough for a first design.

Minimal viable tier

  • Count calls and backward branches with saturating counters sampled at safepoints.
  • Compile whole functions first; avoid loop OSR until function compilation is stable.
  • Support integer/real scalars, branches, direct calls, and simple records first.
  • Bail out to the interpreter for unsupported intrinsics, dynamic values, debugger mutation, and tasks.
  • Use the same RuntimeImage layouts and helper-call interface as the interpreter.

Hard parts

  • Precise value/root maps if a managed heap is introduced.
  • Debugger stepping, live-image updates, forced return, and variable mutation.
  • Exceptions/runtime diagnostics with accurate FPAS source locations.
  • Task suspension across compiled frames.
  • Code-cache invalidation and deterministic testing.

Re-entry gates for a major rewrite

  1. The restored fast interpreter has a stable three-run baseline and no known common-path regression.
  2. Sampling profiles show at least 25% of target workload time in costs the proposed rewrite directly removes.
  3. A small prototype exercises the real production seam, not a synthetic Rust-only loop.
  4. The prototype improves at least two end-to-end workloads and does not regress startup, tasks, or TUI beyond the agreed threshold.
  5. Debugger and artifact compatibility impacts are explicitly accepted; FPAS syntax and semantics remain unchanged.
