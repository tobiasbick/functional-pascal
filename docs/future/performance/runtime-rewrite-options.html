If the interpreter is still too slow, replace the right layer

FPAS is free to replace its bytecode and runtime internals. That freedom is valuable only after the common overhead is measured. These options are deliberately more invasive and should compete against a restored fast-interpreter baseline.

Strong recommendation: retain the six accepted interpreter changes and the accepted bounded managed buffer heap. Fresh A/B medians improved both end-to-end TUI workloads by about 7%, record operations by about 14%, and string concatenation by about 6%. This validates runtime-managed reuse, not a full tracing collector. Compact execution images, tagged heap handles/tracing collection, and tiered compilation remain deferred until evidence identifies material cost still present after buffer reuse.

Reviewed against 77fac915 on 5 September 2026. These alternatives have no evidence-backed priority among themselves. The bounded measurement plan comes first; no new CPU profile was collected in this review.

Three options

A · Compact quickened VM

Keep interpretation, replace 64-bit transport instructions with a compact or predecoded runtime format, resolve metadata once, and introduce profile-backed superinstructions.

Cost: medium · Risk: medium · Deferred pending measured cost attribution

B · Managed heap runtime

A bounded buffer-reuse layer is now implemented and retained. A later major rewrite could replace per-value Arc/COW ownership with tagged slots and handles into a VM-owned tracing heap.

Bounded slice: accepted · Full heap: high cost and risk

C · Native execution

Select JIT or AOT only after reopening the backend decision. A possible JIT design compiles hot verified functions and retains interpreter fallback.

Cost: very high · Risk: very high · Benefit unmeasured in FPAS

Option A — compact, quickened interpreter

The serialized bytecode can remain portable while loading produces a host-private execution image. The execution image may use 32-bit common instructions, side tables for wide operands, resolved function/layout pointers or indexes, and quickened opcodes such as LoadFieldResolved or CallDirectResolved.

Lua demonstrates the value of compact fixed-width register instructions, specialized immediate/constant arithmetic, inline integer-loop handling, and a minimal fetch path. HotSpot demonstrates resolution caches and rewriting/quickening around an interpreter.

portable artifact
  └─ verify + resolve once
       └─ RuntimeImage
            ├─ compact instruction stream
            ├─ resolved call/layout/intrinsic tables
            ├─ cold source/debug metadata
            └─ immutable verifier proof summary

Potential advantages to validate

  • Could improve instruction-cache density and remove repeated table validation; the broader effect is unmeasured.
  • Keeps startup and implementation complexity far below a JIT.
  • Can preserve the existing Value representation initially.
  • Creates a clean input for later native compilation.

Risks and gates

  • Compact formats need escape instructions or side tables for large programs.
  • Quickening must remain deterministic and debugger/source-map aware.
  • Measure code size, load time, dispatch throughput, and full-suite performance. Reject if gains come only from synthetic loops.

Current gate status: not met. Three trusted-image micro-probes failed, and a later runtime look-ahead prototype slowed a workload containing roughly 40 million compare/branch pairs by 3.5%. A different compact encoding still needs sampling evidence that attributes at least 25% of target time to costs it removes.

Option B — tagged slots and a VM-owned heap

The current Rust Value is semantically convenient but ownership crosses every operation. Heap objects are independently reference-counted, records and arrays detach under COW mutation, and recursive drops traverse object graphs. A managed runtime can instead make register/global slots small tagged words and keep arrays, strings, records, closures, and variants in one heap.

Scalar moveClone a Rust enum valueCopy one compact tagged slot

Design variants

  1. Tracing generational heap: may improve allocation throughput, but requires root maps, barriers, safepoints, and debugger integration.
  2. Reference-counted heap with non-atomic local objects: easier migration; promote objects crossing task boundaries to shared ownership. Complexity moves into promotion and cycles.
  3. Region/arena plus immutable values: allocate per call, frame, or TUI render epoch and reclaim in bulk. Excellent when lifetimes align, awkward for globals, closures, and tasks.
  4. Hybrid: compact slots plus generational tracing for ordinary objects and explicit host handles for resources. Its suitability is unmeasured, and it requires a large rewrite.

FPAS-specific recommendation

The bounded production-path prototype is complete. It preserves the 16-byte Value ceiling and Arc/COW semantics while recycling eligible value, pair, and string buffers plus wrapper payload boxes through bounded thread-local pools. Fresh A/B medians improved tui_headless by 7.0%, notes_headless by 7.2%, record operations by roughly 14%, and string concatenation by roughly 6%. Later callback argument and wrapper-box improvements were also retained. Constant caching and inline small aggregates failed their gates; synchronized Record slots regressed TUI by 96.6% and Notes by 33.4%. See the full experiment report.

Keep this layer. Do not infer that a tracing collector will produce the same additional gain: body allocations, atomic reference counts, recursive drops, roots, task sharing, and debugger access still need separate measurement. DHAT attributed 37.5% of allocation events in each TUI workload to selected body sites; it did not measure a 37.5% CPU share. Do not retry synchronized per-object slots. Design compact slots and a VM-owned heap together only when post-reuse profiles show that at least 25% of a target workload is spent in costs that design directly removes.

Option C — native compilation from typed IR

Production compilation already uses target-independent typed IR: program and unit compilation lower to IR and then emit portable bytecode, which the VM executes after verification. A native backend is absent and remains deferred under the Cranelift decision note. Re-entry requires an explicit decision choosing JIT or AOT, a representative release profile, and concrete mappings for verification, values, calls, intrinsics, tasks, and source diagnostics. The tiered sketch below is one possible JIT design if JIT is selected; it is not an agreed implementation plan.

FPAS source → checked typed IR → portable artifact
                               ├─ interpreter (cold/default)
                               └─ hot-function compiler
                                    ├─ native code cache
                                    ├─ safepoint maps
                                    └─ deopt/fallback metadata

HotSpot's lesson is not “add C2”. It is that interpretation, profiling, baseline compilation, optimized compilation, and deoptimization are separate tiers with different jobs. If JIT is chosen, the first experiment should stay bounded to one native tier; its benefit and integration cost still need measurement.

Possible bounded tier, only if JIT is selected

  • Count calls and backward branches with saturating counters sampled at safepoints.
  • Following the Cranelift note, compile one already verified function from the settled register instruction stream; avoid loop OSR in the first slice.
  • Start with integer and Boolean constants, register moves, arithmetic, comparisons, branches, and direct calls.
  • Keep hosted operations, aggregates, strings, closures, tasks, exceptions, and unsupported instructions behind an explicit interpreter fallback boundary.
  • Reuse verifier admission and define the shared value and helper-call interface before generating native code.

Hard parts

  • Precise value/root maps if tagged handles and tracing collection are introduced.
  • Debugger stepping, live-image updates, forced return, and variable mutation.
  • Exceptions/runtime diagnostics with accurate FPAS source locations.
  • Task suspension across compiled frames.
  • Code-cache invalidation and deterministic testing.

Re-entry gates for a major rewrite

  1. The retained interpreter and managed-buffer implementation have a stable current baseline and no known common-path regression.
  2. Sampling profiles show at least 25% of target workload time in costs still present after buffer reuse and directly removed by the proposed rewrite.
  3. A prototype exercises the chosen production seam: a compact execution image for Option A, VM-owned handles/reclamation for Option B, or compiled functions for Option C. A synthetic Rust-only loop is insufficient; heap handles are not a prerequisite for Options A or C.
  4. The prototype improves at least two end-to-end workloads beyond the new managed-buffer baseline and does not regress startup, tasks, or TUI beyond the agreed threshold.
  5. Debugger, task sharing, pause behavior, and artifact compatibility impacts are explicitly accepted; FPAS syntax and semantics remain unchanged.
