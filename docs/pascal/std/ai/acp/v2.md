# `Std.Acp.V2`

A separate nominal family for the pinned ACP v2 protocol. V1 and v2 IDs,
requests, responses and notifications cannot be interchanged implicitly.
Shared lossless values and operational errors remain in `Std.Acp.Types`.

Import `uses Std.Acp.V2 as V2, Std.Acp.Types as Acp;`.
V2 has the same seven root codec pairs and `Decoded*` wrappers described in
[protocol values](types.md). Their signatures use v2 root enums and return the
shared `RawJson` and `AcpError` types. They do not negotiate a connection version.

`V2.Send`, `V2.Notify` and `V2.Respond` use a connection configured for V2 and
the shared [transport/event ownership rules](connections.md). Set
`Options.SupportedVersions` explicitly and supply `V2ClientCapabilities`.
The required initialize `Info` must match `Options.ClientInfo`; its capabilities
must match `Options.V2ClientCapabilities`. Initialization is admitted once.

V2 initialization uses required `Info` and defaulted `Capabilities` fields.
V2 prompt submission, messages, terminal updates and patch fields follow the
v2 schema rather than the v1 payload layout. Consult the generated
[editor declarations](../../../../../lib/api/Std/Acp.V2.fpas) for constructors.

The initialization event is `EventPayload.V2Initialized(Token, Outcome)`.
`InitializeOutcome.Initialized` carries the v2 response. `LowerVersion` retains
`Requested`, `Selected`, and the typed `SelectedInitializeResponse.V1` response.
The connection changes to the selected supported family without resending
initialization. The application must then use the v1 operations explicitly.
An unsupported selection fails initialization and never makes the connection
ready. A v1 peer receiving a v2 offer has not received any v1 client host
capabilities, so those capabilities remain disabled after selection of v1.

V2 `session/prompt` returns acceptance with a message ID. This response does not
mean that work finished. Later session state updates distinguish running,
foreground idle with a stop reason, and background activity. No v1 single-active
prompt guard is imposed on v2. The [v2 console example](../../../../../examples/network/acp-client/README.md)
shows the separate acceptance and idle waits.

New/resume/list/close are v2 baseline methods. Optional delete, additional
directories, image/audio/embedded prompt context and MCP transports use v2
object capabilities rather than v1 Boolean defaults. Resume updates can arrive
before its response. Config IDs and values use the v2 selectors. Authentication
uses `auth/login`/`auth/logout` and the advertised v2 method IDs; terminal methods
use `Host.V2RunTerminalAuthentication` with the common foreground backend.

Permissions retain the v2 subject shape. Content, message, tool, terminal,
plan and patch updates remain typed v2 values; no v1 flattening is performed.
V1 filesystem/terminal request handlers are not advertised as v2 methods.
Experimental features keep their independent [opt-ins](experimental.md), and
MCP uses `V2.SendMcp` with `V2McpResponse` events. All exact/raw numeric, metadata,
bounded-queue and single-use response rules remain the same.
